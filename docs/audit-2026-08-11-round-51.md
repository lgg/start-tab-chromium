# Deep audit round 51 — native new-tab consumption truthfulness

## Scope

Independent continuation from exact `master` commit `5c8431e4eccb19b212a11df02ac7f47a7792a960`. This pass moved away from the already-hardened build/localization layers and audited user-facing runtime boundaries: service-worker messaging, backup/import rollback, Browser Sync verification, Google Drive restore, storage revision transactions, and the native browser new-tab bypass/open/cleanup flow.

## Confirmed defects

1. Native-new-tab polling treated a missing bypass key or a key owned by another tab as success. A lost/replaced grant could therefore produce a false success even though the created tab never confirmed bypass consumption.
2. The bypass expiry was created before `chrome.tabs.update`, but the poller started a fresh timeout only after that navigation call settled. A slow navigation could outlive its grant, then still receive an additional polling window.
3. The expired-grant consumer removed the shared storage key after a separate read. That stale read/remove sequence could erase a newer retry grant.
4. Grant publication and consumer `get` → `set(consumedAt)` were not serialized with each other. A delayed consumer from an older URL attempt could overwrite a newer retry grant with its stale `expiresAt` and consumed state.
5. The central self-hosted CI contract's explicit regression-command list had stopped at Round 49. Round 50 remained protected by its own static validator, but the central contract no longer mirrored the complete pipeline.

## Corrections

- Native-new-tab success now requires `consumedAt` on the exact `tabId` and exact `expiresAt` grant. Missing, foreign, or replaced ownership fails closed.
- One absolute expiry is created before navigation and is reused by polling; navigation time now consumes the same timeout budget instead of receiving a second window.
- Expired consumers return `false` without deleting the global bypass key; opener-owned cleanup handles stale grants safely.
- Grant write, consume read-modify-write, and owned cleanup share the existing `withStorageLock("native-new-tab-bypass", ...)` boundary. Polling never holds that lock, so tab-event consumption remains able to complete.
- Round 51 deterministic fixtures cover normal consumption, expiry during navigation, missing/foreign ownership, expired-consumer cleanup, total temporary-tab cleanup, and a delayed first-attempt consumer racing a retry.
- The self-hosted CI command contract is brought forward through Rounds 50 and 51.

## Validation boundary

Automation exercises the native-new-tab state machine with deterministic Chrome API mocks, historical regression contracts, TypeScript typechecking, and all extension build profiles. Physical vendor-specific native-new-tab URLs and visible browser UI behavior still require interactive Chromium testing; `docs/manual-qa-round51.md` records that final browser-level checklist.
