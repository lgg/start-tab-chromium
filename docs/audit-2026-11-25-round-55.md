# Round 55 — exact backup revision tokens and remote decision revalidation

Base is the tested Round 54 tree, with prior Round 53 protections intact.

## Confirmed defects
- The effective local revision used max(stored, legacy fallback), which could hide a real increment of a valid stored counter when imported settings/runtime timestamps were larger.
- A legacy profile's first revisioned write could store exactly the fallback value; comparing only numbers incorrectly accepted the obsolete local snapshot.
- Browser Sync checked local revision under data-write but persisted matching metadata after releasing the lock.
- Smart Sync selected an upload based on an old remote observation, then fetched a newer remote frame for quota accounting without validating that the original decision still applied.

## Corrections
- Use the persisted revision as authoritative whenever present and carry the exact stored counter (or null for legacy absence) alongside the fallback. Every guarded local JSON/recovery, Chrome Sync and Google Drive path compares the stored token and effective revision.
- Commit Browser Sync acceptance metadata within the same local revision lock.
- Pass the observed remote metadata (including absence) into Smart Sync writes and compare it during quota inspection and immediately before writing. Retry the complete conflict-resolution decision on observed remote/local conflict, with the existing bounded retry count. Explicit user-requested upload still means overwrite.
- Extend executable fixtures and evolve the existing Round 52 static contract without weakening its earlier guarantees.

## Validation boundary
Chrome storage.sync is not a distributed compare-and-swap database. A different physical device can still change remote state after the last observed metadata check, or after a local upload is confirmed. The changes prevent overwriting newer frames already observed locally before the write, not all theoretical distributed races. Real multi-device testing remains required.
