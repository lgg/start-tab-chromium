# Round 61 — local revision tokens after backup restore

A backup can contain older or identical numeric settings, block, theme and runtime revisions. Copying those revisions directly into local storage allows an already-open editor to mistake restored content for the version it originally read. This is an ABA-style optimistic-concurrency failure.

During import, under the data-write lock and before destructive mutation, allocate a fresh local revision above the current normalized settings, runtime, entities, tasks, persisted counter and wall clock. Stamp the restored settings/runtime and entity edit tokens, while preserving semantic content and created-at values. The semantic Browser Sync checksum intentionally excludes these generated stamps. Keep the global revision at least as large as the local restore stamp; preserve the incoming remote revision floor where applicable. The recovery snapshot and rollback retain the original local revisions exactly. Reject exhausted unsafe revision ranges rather than silently reusing a token.

Regression coverage exercises colliding timestamps, stale block/theme/layout edits, repeated restore, and unchanged semantic checksum. Real browser and multiple-device acceptance remain outstanding. Note values use their own content CAS; this change does not promise to detect every ABA transition for notes.
