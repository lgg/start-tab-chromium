# Round 53 — Drive backup and revision boundary audit

Base: master ccefde6f6266de643ab9b2aa2b4a896fe3233403.

## Confirmed defects and corrections

- Drive files.list can return an empty page with a continuation token. Follow the token, request it explicitly in fields, and stop only at a terminal page or a valid matching file. Reject malformed pages, repeated tokens, or an exhausted page budget rather than creating a duplicate backup.
- Two simultaneous uploads in the same extension profile could both see no file, create duplicate backups, or write an older snapshot after a newer one. Serialize lookup, snapshot capture and writes under the google-drive Web Lock. Restore uses the same lock but captures its local revision before queueing, preserving the destructive-restore CAS.
- Check the captured revision before and after Drive upload. An intervening edit produces a visible conflict; the remote upload may already have completed, so repeat the upload to capture the latest state. Do not promise rollback of a completed remote operation.
- Browser Sync previously accepted finite but unsafe numeric revisions. At sufficiently high magnitudes incrementing by one no longer changes a JavaScript number, invalidating the optimistic revision check. Reject unsafe/exhausted local revision reads and writes, and reject invalid current-version Sync metadata before remote overwrite or restore.
- Encode Drive file IDs in request URLs.

## Tests

Added executable regression scenarios to the existing Round 52 fixture entrypoint, which is already run by npm test and the dedicated Windows CI. Scenarios cover empty and repeated listing pages, simultaneous uploads, changes during upload, poisoned remote revision and already-corrupted local revision. The existing Round 52 restore tests remain intact.

## Boundaries

This change serializes operations inside one extension profile with Web Locks; separate physical devices remain independent. Google Drive does not provide a global compare-and-swap transaction here. Real OAuth, multi-device propagation, browser-level interaction and a fresh full CI run are still required. This is a focused source audit, not an assertion that every module has been reviewed or that no other bugs exist.
