# Deep audit round 52 — remote backup optimistic concurrency

## Scope

Independent continuation from exact `master` commit `d02d8b4c1b924c8379f7f7ccd720421c6372b99d`. This pass moved away from Round 51 native-new-tab work and audited Browser Sync conflict resolution, backup import transaction boundaries, Google Drive restore, cross-context storage revisions, DNR rollback, and remote I/O windows where another extension tab can save newer local data.

## Confirmed defects

1. **Browser Sync remote-wins lost update.** `syncChromeSyncBackup()` captured local backup content and its revision while holding `data-write`, released that lock for remote verification/conflict resolution, and later called `importBackup()`. A different extension context could save newer local data in that gap. The already-decided remote restore would then reacquire `data-write` and overwrite the newer edit.
2. **Browser Sync upload could report success for a stale local snapshot.** Local data could change after `prepareSnapshot()` but during remote metadata/quota/commit verification. The old upload path had no post-snapshot revision validation, so remote content and local sync metadata could lag the state that existed when the operation returned.
3. **Explicit Browser Sync Restore had the same destructive network window.** A user could confirm Restore, another tab could save while remote metadata/chunks were downloaded, and the import would silently erase that later edit.
4. **Google Drive Restore had the same lost-update class across its list/download requests.** There was no local revision precondition connecting the pre-network state to the eventual destructive import.

## Corrections

- Added `StartTabDataRevisionConflictError` and an exact optimistic revision guard that uses the same fallback value as the captured revision. This preserves comparability for legacy profiles that did not yet have `startTabDataRevision` until their first revisioned mutation.
- `exportBackupSnapshot()` now returns both the captured data revision and its fallback.
- `importBackup()` accepts an expected current revision. The guard runs **inside `data-write` and before the pre-import recovery snapshot, storage writes, DNR reconciliation, alarms, or revision mutation**, so a conflict is side-effect free.
- Browser Sync carries the captured revision token with every prepared snapshot. Remote upload checks that token immediately before `chrome.storage.sync.set()` and again after the committed remote frame is verified, before local sync metadata is accepted.
- Manual Browser Sync Upload retries revision conflicts up to a small bounded limit, taking a fresh snapshot each time. It therefore converges to a stable local snapshot instead of returning success for a stale frame.
- Smart Browser Sync retries the entire conflict-resolution decision on a local revision conflict. A stale `remote wins` decision can never be reused after another tab saves; the retry compares the new local revision/content with the current remote state.
- The `unchanged` Browser Sync path also validates that its captured local revision remained current before publishing matching local sync metadata.
- Explicit Browser Sync Restore captures a local revision before remote I/O and fails closed if another context changes Start Tab data before import. It intentionally does not silently retry a destructive Restore over the newer edit.
- Google Drive Restore captures the same revision token before listing/downloading the remote backup and passes it to the atomic import precondition.

## Regression coverage

Round 52 fixtures deterministically reproduce the original interleavings with Chrome API mocks: stale backup CAS rejection before any recovery/DNR/alarm side effect; automatic Browser Sync taking a rev-150 snapshot, receiving a rev-300 local edit while reading a rev-200 remote bundle, then recalculating and uploading rev-300; local mutation from inside `storage.sync.set()` forcing Upload to retry; explicit Browser Sync Restore preserving an edit made during remote chunk download; and Google Drive Restore preserving an edit made during the media download.

The static contract requires the CAS ordering, Browser Sync pre/post remote commit checks, bounded retry behavior, explicit Restore guard, Google Drive guard, test wiring, CI ordering, and documentation.

## Validation boundary

Automation can deterministically exercise storage, remote-frame, DNR/alarm side-effect, and network-window interleavings. Physical multi-profile Chrome Sync propagation timing and live Google OAuth/Drive behavior still require interactive Chromium testing; `docs/manual-qa-round52.md` records those final browser-level checks.
